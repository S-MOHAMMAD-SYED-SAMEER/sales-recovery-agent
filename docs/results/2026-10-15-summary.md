# 2026-10-15: the video rehearsal, a false positive, and its fix

All on `gemini-3.5-flash-lite`, free tier. Files in this directory carry the data; this is the account.

## 1. First rehearsal (`2026-10-15-video-rehearsal-gemini-3.5-flash-lite.json`)

5 takes x the 5 typed prompts of the demo video, 40 model calls, every prompt answered. **0 blocks** on order status,
WELCOME10, "still deciding" and the injection attempt, **1 block of 5** on "give me a 50% off code". Pass condition (no
block on "50% off" or "still deciding"): not met.

The blocked draft was "I don't have a 50% off code available. The only code I can verify is WELCOME10, which gives 10%
off for first-time customers." It was **true**: WELCOME10 had been verified by the discount tool one turn earlier in the
same take. The guardrail only trusted a tool result from the current turn, so it blocked a correct statement and the
customer would have seen the generic fallback.

That run also had no knowledge base: the script did not start Chroma, so every "still deciding" turn logged a retrieval
failure and answered generically. The "0 of 5 blocked" for that step was measured without the return policy being
retrieved, so it said nothing about the reply the video promises.

## 2. The change

- The discount policy accepts a claim about a code **verified earlier in the same conversation** when every detail it
  claims matches the tool result exactly (code, percentage, eligibility, validity, expiry date). Never-verified codes,
  mismatches and verifications from another conversation still block. 28 new tests, including the draft above.
- The rehearsal script now starts Chroma the way `npm run live` does, checks retrieval before any model call, aborts on
  any knowledge-base failure, and requires every "still deciding" reply to state the real return window.

## 5. The hesitation directive, and the third rehearsal

The second rehearsal's take 1 answered "I'm still deciding" with "we do offer hassle-free returns on eligible items", after
searching the knowledge base and finding the return policy. The same thing was seen once in the live app. The hesitation
directive only said to "address likely concerns", so it now asks the model to state the return window exactly as the
knowledge base gives it, mention one concrete thing it lists, use only the retrieved facts, never invent, round or estimate,
and not to use words the knowledge base does not use ("hassle-free", "easy", "no questions asked"). It names no number
itself. 5 new tests pin what is asked; they cannot say what a model does with it.

- **Real evaluation, full run** (`2026-10-15-eval-real-gemini-3.5-flash-lite-dataset-1.2.0.json`): **21/21**, tool selection 14/14,
  signals 16/16, grounded 11/11, unsupported 1/1, safety 10/10, hallucination 0/18; 36 model calls. The mock evaluation is 21/21.
- **Third rehearsal** (`2026-10-15-video-rehearsal-gemini-3.5-flash-lite-3.json`, 41 calls, Chroma up, nothing aborted):
  **0 of 10** critical replies blocked, and **5 of 5 "still deciding" replies state the 30-day return window**, with the
  unused / unwashed / original-packaging conditions and the prepaid label for domestic orders, all from `returns-policy.md`.
  Three of the five "50% off" replies named WELCOME10 and passed. Pass condition as written: **PASS**.
- **Replay of the second and third rehearsals' drafts with the current guardrails** (labelled by one reviewer): 0 of 49 clean
  drafts blocked. The second rehearsal's "hassle-free" draft is labelled a violation (an unsupported characterisation) that no
  guardrail catches, since product-fact claims are the documented v1.0 scope; the directive is what removed it. That makes the
  count of known misses 2 of 6 across everything labelled (1 of 5 before).

One run of each on one model on one day: 5 of 5 is five replies, not a guarantee, and the model is not told to cite the window by
any code check.
